ADDS: Security: LSASS crash (0xc0000409) when Kerberos accesses a file share due
to corrupt list on Windows 11 24H2 / Windows Server 2025 Important: This was
authored via https://aka.ms/contentidea. Follow Content Idea (CI) 200092 link
for any updates. Author: Ryan Ries Summary/Symptom A Windows 11 24H2 client or
Windows Server 2025 machine attempts to access a file share, and lsass crashes.
Subsequently the machine reboots. The user may not realize what the trigger is
and it may appear as though the machine is crashing randomly. This occurs on
machines that are fully up to date (as of the time of this writing) with the
February 2025 hotfix. A crash has been observed when accessing a cloud (AAD)
file share, and also crashing while accessing an onprem file share. Both
scenarios appear to be affected. Exception details c0000409

TTD is impossible due to the virtual machines having RunAsPPL enabled with UEFI
lock, and RunAsPPL cannot be disabled because it would require running the UEFI
opt-out tool and it would require physical access to the machine at a very early
phase during boot, which is not possible in an AVD environment. lsass crashes
while attempting to acquire a Kerberos service ticket for
cifs/pii_removed.file.core.windows.net. When lsass attempts to acquire this
Kerberos service ticket, it first looks in the local SPN cache. It did not find
the cache entry there, so it goes on to query the SPN Oracle. This of course is
an Azure endpoint that requires Cloud Kerb and so the KDC proxy is a
login.microsoftonline.com/tenant-id/kerberos URL. So now we have a cache entry
for the KDC Proxy cache so we try to add that cache entry to the KDC Proxy
cache. Problem is, that cache is uninitialized. In the simplest terms we attempt
to add an object to an uninitialized linked list, and this makes lsass explode.
KerbInitKdcProxyCache must be called prior to adding anything to this cache.
KerbCleanupKdcProxyCache unitializes the cache. Probably every time the cache is
emptied out. But it seems we have a race condition where someone has called the
uninitialize function first, then we try to add something new to the list
without re-initializing the list first. Cause I have proposed the following to
fix to the crash from VOIDKerbCacheKdcProxyCacheEntry( __in PKDC_PROXY_CACHE
KdcProxyCache, __inout PKDC_PROXY_CACHE_ENTRY CacheEntry ){
D_DebugLog((DEB_TRACE_KDC, "cache proxy cache entry %p for domain %wZ\n",
CacheEntry, &CacheEntry->DomainName)); KerbLockKdcProxyCache(); InsertHeadList(
&KdcProxyCache->CacheEntries.List, &CacheEntry->ListEntry.Next );
KerbUnlockKdcProxyCache();} To this: VOIDKerbCacheKdcProxyCacheEntry( __in
PKDC_PROXY_CACHE KdcProxyCache, __inout PKDC_PROXY_CACHE_ENTRY CacheEntry ){
D_DebugLog((DEB_TRACE_KDC, "cache proxy cache entry %p for domain %wZ\n",
CacheEntry, &CacheEntry->DomainName)); NT_ASSERTMSG("KdcProxyCache->Initialized
== TRUE", KdcProxyCache->Initialized); KerbLockKdcProxyCache();if
(KdcProxyCache.Initialized) { InsertHeadList( &KdcProxyCache->CacheEntries.List,
&CacheEntry->ListEntry.Next ); } KerbUnlockKdcProxyCache();} This safeguard is
already in place in several other functions through the same source code file.
