Windows 11:NET: Wi-Fi fails to connect automatically after GP update when
fMinimizeConnections and fBlockNonDomain transition from 3,1 to 0,0 respectively
Important: This was authored via https://aka.ms/contentidea. Follow Content Idea
(CI) 198835 link for any updates. Author: Bharath Kumar M Summary/Symptom The
customer is implementing a security baseline called CIS Baseline Security GPO,
which has WCM configuration to disables simultaneous network connections and
blocks any new network connections when a domain authenticated connection is
already present. This security baseline policy sets the WCM settings
fMinimizeConnections to 3 and fBlockNonDomain to 1. This Group Policy is applied
to all Windows 11 devices in the environment. However, the customer wants to
create an exception to allow multiple network connections for a specific set of
devices. They created another Group Policy with WCM settings
fMinimizeConnections set to 0 and fBlockNonDomain set to 0. Baseline Security
GPO is also enabling “Process even if the Group Policy objects have not changed”
setting. The issue arises when the first Group Policy is processed, causing the
Wi-Fi interface to disconnect as expected. However, when the second Group Policy
is processed, the Wi-Fi should automatically reconnect, but it does not do so.
Repro Steps: Customer has setup two GPOs in the following way in an OU
containing Windows 11 machines.The 1st GPO having lowest precedence is setting
the below to all Windows 11 machines, Apply the settings as specified in CIS
Baseline Security GPO which also contains the below WCM settings.
fMinimizeConnections to 3 to block Wi-Fi Connection when connected to Ethernet.
fBlockNonDomain to 1 to prevent connections to both a domain-based network and a
non-domain-based network at the same time. The 2nd GPO having higher precedence
is setting the below to few Windows 11 machines through GPO machine account
security filtering to exempt them from above strict WCM policy,
fMinimizeConnections set to 0 fBlockNonDomain to 0. Let’s say we have a client
in the exemption category (WCM settings of Winning GPO - 2nd GPO) and with the
above GPO configuration in place, perform a gpupdate with Ethernet and Wi-Fi
connected to CORP network. Both connections are needed to reproduce the issue.
Wi-Fi gets disconnected and it does not connect automatically. Even when
Ethernet is unplugged later, Wi-Fi does not auto-connect. Expected Behaviour:
Wi-Fi should reconnect automatically. Cause This issue is identified as bug in
Windows 11 ( 21H2 /22H2 /23H2 /24H2) Operating system Bug 55459382: Win11: Wi-Fi
fails to connect automatically after GP update when fMinimizeConnections and
fBlockNonDomain transition from 3,1 to... - Boards Article resolution Verified
workarounds: 1. Once disconnected, disable and re-enable the Wi-Fi adapter, to
let Wi-Fi connect automatically. 2. Set “Process even if the Group Policy
objects have not changed” to disabled. 3. Organize the GPOs linked in the
Windows 11 OU such that, GPO 1 – “Applies baseline security settings (except WCM
settings) to all computers” GPO 2 – “Applies the fMinimizeConnections=3,
fBlockNonDomain=1 to all computers with exempted computers in the Deny List” GPO
3 – “Applies the fMinimizeConnections=0, fBlockNonDomain=0 only to the exempted
computers” 4. The other possibility is to restart the WCM service after the
group policies have been applied. This will then auto-reconnect the Wi-Fi. But
during the application of the GPOs the Wi-Fi gets disconnected and would only be
re-connected after restarting the WCM when Group Policy is completed. More
information +++++++++++ MS INTERNAL Do not share with customer +++++++++++++++
WCMSvc gets the notification as GPO changes are applied, and we will review the
2 stages below, 1. fMinimizeConnections to 3 and fBlockNonDomain to 1 2.
fMinimizeConnections to 0 and fBlockNonDomain to 0 (After GP Registry extension
processing is completed – Settings of 2nd GPO - Winning)For 1st set of
notification,1. fMinimizeConnections=3 and fBlockNonDomain=1 values are read,
with Wi-Fi connected still.2. EvaluateDomainDomainPolicyAction () identifies no
conflict between Ethernet and Wi-Fi as both are domain-authenticated.3.
TokenManager::Evaluate calls to ApplyStrictMinimizePolicyFilter() which clears
all tokens for Wi-Fi interface as Ethernet is already connected
(fMinimizeConnections=3).4. WCM is later notified of Wi-Fi disconnection through
the event “wcm_notification_cde_disconnected” and
EvaluateDomainDomainPolicyAction() is called as result of network status
change.5. EvaluateDomainDomainPolicyAction() disables AutoConnect token for Wi-
Fi and marks the action as “DisconnectAndDenyAutoConnect” as
fBlockNonDomain=1.The reason is that as we have a domain-authenticated Ethernet,
Wi-Fi is disconnected currently, hence Wi-Fi auto-connect to be blocked.For 2nd
set of notification, 1. fMinimizeConnections=0 and fBlockNonDomain=0 values are
read again. 2. EvaluateDomainDomainPolicyAction() is called, does not reset the
Action set on the list of interfaces and returns early. 3.
TokenManager::Evaluate() -> ApplyDomainPolicyFilter() ->
GetDomainPolicyActionForInterface () returns the stale value
“DisconnectAndDenyAutoConnect” that was calculated when the settings were
fMinimizeConnections=3 and fBlockNonDomain=1.4. Wi-Fi interface does not have
the auto-connect token after the last GP change notification and needs to be
connected manually.Detailed Analysis:Ethernet GUID –
